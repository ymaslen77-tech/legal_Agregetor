# Архитектура, разработка и публикация сайта «ПравоПоиск»

> **Статус:** единый стандарт целевой инфраструктуры и выпуска проекта.  
> **Актуализировано:** 15 октября 2026 г.  
> **Важно:** нормативная схема ниже не означает, что все её компоненты уже развёрнуты. Фактическое состояние и незавершённые работы указаны отдельно.

## 1. Полная схема разработки, размещения и работы сайта

| № | Компонент | Назначение | Основная среда |
| --- | --- | --- | --- |
| 1 | **Локальная разработка** | Программирование, создание страниц и API, локальная отладка и тесты | Компьютер разработчика, Node.js, Docker |
| 2 | **GitHub — репозиторий** | Исходный код, ветки, коммиты, история изменений, Pull Requests и ревью | [ymaslen77-tech/legal_Agregetor](https://github.com/ymaslen77-tech/legal_Agregetor) |
| 3 | **GitHub Actions — CI/CD** | Проверка типов, сборки, линтеров, unit/E2E и регрессионных тестов; выпуск только после успешных проверок. Миграции БД запускаются контролируемо по отдельным правилам | GitHub Actions |
| 4 | **Vercel — основной хостинг** | Развёртывание Next.js, SSR, серверные маршруты/API Routes, CDN, HTTPS, production/preview | Vercel, проект `pravopoisk` |
| 5 | **Neon — PostgreSQL** | Постоянные данные, пользователи, юристы, вопросы/ответы, документы, индексы, связи, транзакции, ветки базы | Neon, проект `purple-sun-53026244` |
| 6 | **Домен и DNS** | Публичный адрес, DNS-маршрутизация на Vercel, TLS/HTTPS и канонический адрес | DNS-провайдер + домен Vercel или отдельный домен |
| 7 | **Пользователи сайта** | Просмотр страниц, поиск, регистрация/авторизация, работа с юридическими инструментами и личными кабинетами | Браузер → Vercel → серверная логика → Neon |

**Поток разработки:**

```text
Локальная разработка → GitHub → GitHub Actions → Vercel ↔ Neon
```

**Поток пользовательского запроса:**

```text
Пользователь → Домен/DNS → Vercel → Next.js / серверная логика → Neon
                                                ↘ объектное хранилище (по мере подключения)
```

GitHub не является хостингом работающего приложения или основной базой данных. Vercel размещает и выполняет приложение, Neon хранит PostgreSQL-данные. Домен и DNS направляют пользовательский трафик к Vercel.

## 2. Дополнительные компоненты инфраструктуры

| Компонент | Назначение | Целевое размещение | Статус реализации |
| --- | --- | --- | --- |
| **Фоновые задачи** | Длительные операции, обработка очередей, импорт, массовые обновления | Отдельный worker или Neon Functions | **Планируется**; отдельный production-worker не подтверждён |
| **Планировщик** | Регулярные обновления, проверки, очистка и регламентные задания | Vercel Cron / Neon Functions или внешний планировщик | **Планируется**; наличие production-расписаний не подтверждено |
| **Файловое хранилище** | PDF, изображения, вложения и прочие загруженные файлы | S3-совместимое объектное хранилище | **Не завершено**: код поддерживает локальный и S3-режимы, боевое объектное хранилище и перенос вложений требуют проверки |
| **Авторизация** | Регистрация, вход, сессии, проверка ролей и доступа | Приложение с данными пользователей в Neon; Neon Auth — только возможный вариант развития | **Реализована в приложении** собственная сессионная логика с JWT/ролями; переход на Neon Auth не заявлен |
| **Мониторинг** | Состояние релизов, логи, ошибки, производительность, доступность | Vercel и, при необходимости, внешняя система наблюдаемости | **Частично**: доступны Vercel deployment/runtime logs; внешняя система и оповещения не подтверждены |
| **Резервное копирование** | Восстановление БД, критических файлов, ключей и конфигурации | Возможности Neon + **независимые** резервные копии PostgreSQL и объектов | **Частично**: создан локальный `pg_dump` исходной БД; регламент автоматических независимых бэкапов не подтверждён |
| **Защита** | HTTPS, секреты, ограничения доступа, валидация API, разграничение прав | Vercel + приложение + Neon | **Частично**: HTTPS, секреты окружения и серверные права доступа; полная security-приёмка не подтверждена |

**Правило:** перечисление альтернатив (Neon Auth, Neon Functions, Vercel Cron, S3, worker) не означает их фактическое включение. Сначала документировать выбор, права, затраты, отказоустойчивость и тесты, затем вводить в эксплуатацию.

## 3. Стандарт разработки, приёмки и публикации

1. **Development.** Изменения выполняются локально. Разработчик запускает профильные тесты, typecheck, lint, сборку и проверяет последствия для схемы данных.
2. **GitHub Branch.** Каждая отдельная задача разрабатывается в своей ветке; `main` — только проверенное, принятое состояние.
3. **Pull Request.** PR содержит описание, риски, изменённые маршруты/таблицы, способы тестирования и план отката. Включаются обязательные GitHub Actions; замечания и ошибки устраняются до merge.
4. **Preview Deployment.** Vercel создаёт предварительное развёртывание для проверки интерфейса, SSR и API. Preview не должен случайно записывать данные в production.
5. **Staging Database.** Для интеграционных проверок использовать отдельную ветку/БД Neon с ограниченным доступом, минимально необходимыми и обезличенными данными. Проверять миграции и откат на репрезентативной схеме.
6. **Merge в main.** Выполняется после успешных обязательных проверок и согласования изменений; для критических релизов — после ручной приёмки.
7. **Production Deployment.** Vercel автоматически развёртывает проверенный `main` при наличии доступных квот и корректной интеграции. Каждый релиз проверяется по точному SHA, статусу `READY`, окружению, URL и runtime-логам.
8. **Database Migrations.** Миграции выполняются **отдельным управляемым шагом**, через `prisma migrate deploy` и только на нужной БД, с бэкапом, проверкой и записью результата. Для совместимости с релизом миграция может потребоваться **до** переключения трафика: порядок определяет совместимость схемы и кода (expand → migrate → contract), а не формальная нумерация шагов.
9. **Monitoring.** Проверять HTTP-доступность, главную страницу, Q&A, профили юристов, авторизацию, защищённые API, чтение/запись БД, журналы и метрики ошибок после релиза.
10. **Rollback.** При неисправности вернуть предыдущий **проверенный** deployment. Восстановление PostgreSQL — отдельная процедура (Neon branch/backup, оценка потерь данных, совместимость версий и явное разрешение). Откат кода сам по себе не откатывает транзакции в БД.

### Обязательные ограничения для production

- Секреты `DATABASE_URL`, `JWT_SECRET`, `AUTH_SECRET`, `DOCUMENT_STORAGE_KEY` и ключи внешних провайдеров — только в защищённых настройках среды; не в Git, README, браузере, логах и PR.
- Перед каждой миграцией проверять целевой проект Neon, имя БД и ветку. Приложению на Vercel нужен pooled URI; для `pg_dump`, `pg_restore` и миграций использовать **прямое** подключение.
- **Запрещено запускать `prisma:seed` / `prisma db seed` в production.** В текущем проекте `prisma/seed.ts` вызывает `clearData()` и удаляет записи приложения. Не применять `prisma db push` к production.
- Миграции не должны автоматически выполняться на каждой сборке без ограничений доступа и проверок; для production требуется контролируемый процесс.
- Не смешивать production и staging `DATABASE_URL`; тестовые и демонстрационные записи не должны появляться в рабочей публичной базе.
- Для персональных данных обязательны разграничение доступа по владельцу, безопасные логи, ограничение хранения и проверка процессов восстановления.
- Для резервных копий определяются RPO/RTO, расписание, срок хранения, шифрование, хранение ключей и регулярное **пробное восстановление**.
- Для файлов отдельно сохранять содержимое S3/`public/uploads`/Docker volumes; SQL-дамп не содержит байты файлов, находящихся вне БД.

## 6. Итоговая целевая архитектура

```text
Разработка → GitHub → GitHub Actions → Vercel ↔ Neon
Пользователь → Домен/DNS → Vercel → Серверная логика → Neon
```

Это **целевой стандарт промышленной эксплуатации**: автоматизация публикации, контроль изменений, разделение тестовой и рабочей среды, управляемые миграции, мониторинг, защита, резервирование и восстановление. Новые инфраструктурные компоненты вводятся по мере необходимости и только после проверки.
