# ПравоПоиск — архитектура разработки, размещения и эксплуатации

Статус: **целевой архитектурный стандарт проекта**, с отдельным учётом фактически внедрённых компонентов.  
Актуализировано: **15 октября 2026 г.**

Этот документ определяет единую схему разработки, CI/CD, публикации, хранения данных и эксплуатации сайта. Функциональность, отмеченная как целевая, **не считается внедрённой** до отдельной технической приёмки.

## 1. Полная схема разработки, размещения и работы сайта

| № | Уровень | Назначение | Ответственный компонент |
| --- | --- | --- | --- |
| 1 | **Локальная разработка** | Программирование, проверка, отладка, миграции в изолированной среде | Рабочая машина, Node.js, Docker и тестовая PostgreSQL |
| 2 | **GitHub — репозиторий** | Версионирование кода, отдельные ветки, история, Pull Requests и ревью | [ymaslen77-tech/legal_Agregetor](https://github.com/ymaslen77-tech/legal_Agregetor) |
| 3 | **GitHub Actions — CI/CD** | Автоматическая проверка типов, линтинг, тесты, сборка, аудит безопасности и контроль миграций | Workflows GitHub Actions |
| 4 | **Vercel — основной хостинг** | Сборка и публикация Next.js, SSR, Route Handlers / API, HTTPS, Preview и Production | Проект Vercel `pravopoisk` |
| 5 | **Neon — PostgreSQL** | Таблицы, пользователи, юридические данные, Q&A, транзакции, отдельные ветки БД | Проект Neon `purple-sun-53026244` |
| 6 | **Домен + DNS** | Публичный адрес, DNS-записи, подключение домена к Vercel, сертификат HTTPS | DNS-провайдер + Vercel |
| 7 | **Пользователи сайта** | Просмотр страниц, регистрация, авторизация, вопросы и ответы, профили юристов, юридические сервисы | Браузер → Vercel → серверная логика → Neon |

**Границы ответственности:** исходный код не хранится в Neon; база данных не размещается в GitHub; Vercel исполняет Next.js-приложение и обращается к Neon по защищённому серверному соединению. Браузер не должен получать `DATABASE_URL` или другие серверные секреты.

## 2. Дополнительные компоненты инфраструктуры

| Компонент | Назначение | Размещение / стандарт |
| --- | --- | --- |
| **Фоновые задачи** | Долгие операции, обработка очередей, повторные попытки | Отдельный worker / Neon Functions — **целевой вариант**, требуется внедрение и выбор исполнителя |
| **Планировщик** | Регулярные обновления и задания | Vercel Cron / Neon Functions или иной планировщик — **по результатам реализации** |
| **Файловое хранилище** | PDF, изображения, вложения, пользовательские файлы | S3-совместимое постоянное хранилище — **целевая архитектура**; локальные файлы Docker должны мигрировать отдельно |
| **Авторизация** | Регистрация, вход, сессии, роли и контроль доступа | **Сейчас:** логика приложения и PostgreSQL; Neon Auth — **возможная будущая замена**, без автоматической миграции |
| **Мониторинг** | Логи, ошибки, доступность, производительность и оповещения | Vercel + внешняя система — внешние алерты внедряются отдельно |
| **Резервное копирование** | Восстановление БД, файлов и критических секретов | Neon и **независимые проверенные резервные копии**, отдельное восстановление вложений |
| **Защита** | HTTPS, секреты, роли, ограничения API, доступ к БД | Vercel / приложение / Neon; принцип минимальных прав, отсутствие секретов в Git и браузере |

Для асинхронных заданий нельзя полагаться на длительные HTTP-запросы Vercel без проверки лимитов исполнения. Персистентные файлы нельзя хранить как единственную копию в файловой системе serverless-развёртывания.

## 3. Стандарт работы и публикации

Все функциональные изменения проходят отдельную ветку, проверку и контролируемую публикацию:

1. **Development.** Разработка локально, проверка сборки и тестов; работа с локальной/изолированной БД, без копирования реальных персональных данных без необходимости.
2. **GitHub Branch.** Создание отдельной ветки от актуальной `main`; изменения кода, документации и миграций фиксируются в Git.
3. **Pull Request + GitHub Actions.** Ревью изменений, TypeScript, lint, модульные/интеграционные/E2E-проверки, сборка; при изменении БД — ревью SQL и совместимости.
4. **Preview Deployment.** Vercel создаёт предварительную версию по PR, **если для этого настроена и доступна Git-интеграция**. Проверяются приложение, безопасность, маршруты и пользовательские сценарии.
5. **Staging Database.** Отдельная ветка БД в Neon (или отдельная тестовая БД) для Preview/Staging. Никакие тестовые или разрушительные операции не выполняются на production-данных.
6. **Merge в main.** Только после обязательных успешных проверок, разрешения блокирующих замечаний и подтверждения совместимости с БД.
7. **Production Deployment.** Vercel публикует новую версию с `main` через Git-интеграцию; проверяются точный commit SHA, окружение, секреты и статус `READY`. `READY` не заменяет проверку функций сайта.
8. **Database Migrations.** Версионированный `prisma migrate deploy` — **отдельный контролируемый этап** после тестирования в Staging, с планом отката. Реальный порядок относительно развёртывания выбирается по совместимости: безопасные расширения схемы до переключения трафика, удаление старого — позже, отдельным релизом. Не выполнять разрушительные изменения автоматически.
9. **Monitoring.** Проверка HTTP-ответов, входа, прав доступа, Q&A, карточек юристов, логов Vercel, запросов Neon, ошибок и производительности.
10. **Rollback.** Откат Vercel на ранее проверенное развёртывание. Для изменённой БД — **отдельный план восстановления данных и схемы**, поскольку откат кода сам по себе не откатывает PostgreSQL.

### Обязательные правила для базы

- `DATABASE_URL` хранится только как секрет окружения Vercel; для serverless-приложения используем pooled-подключение, для `pg_dump`/`pg_restore`/миграций — direct-подключение.
- Миграции проверяются сначала на отдельной ветке/копии БД; запрещено применять потенциально разрушающие SQL без оценки данных и резервной копии.
- **Никогда не запускать `npm run prisma:seed` / `prisma db seed` на рабочей базе:** текущий `prisma/seed.ts` вызывает `clearData()` и удаляет существующие записи. Seed предназначен только для изолированного окружения.
- Не применять `prisma db push` к рабочей БД вместо миграций. Не запускать автоматическое восстановление дампа поверх текущей production-БД.
- При обновлении `DATABASE_URL` необходимо **новое развёртывание Vercel**, затем контрольный запрос к реальным данным сайта.
- Производственные пароли, `JWT_SECRET`, `AUTH_SECRET`, `DOCUMENT_STORAGE_KEY` и AI API-ключи не записываются в Git, документацию или логи. Потеря ключа шифрования сохранённых документов делает их недоступными.
- Архив `pg_dump` **не включает** файловые вложения из `public/uploads` и Docker-volume с приватными вложениями: проверять и переносить их отдельно.

## 4. Разделение окружений

| Среда | Код | База | Требования |
| --- | --- | --- | --- |
| **Development** | Локальная ветка | Локальная PostgreSQL в Docker | Безопасные тесты и независимые локальные настройки |
| **Preview** | GitHub PR / Vercel Preview | Изолированная Neon-ветка | Не подключать к production для мутационных тестов |
| **Staging** | Кандидат релиза | Отдельная ветка/копия Neon | Тестирование миграций и полного сценария публикации |
| **Production** | Одобренная `main` | Проверенная рабочая Neon PostgreSQL | Секреты, бэкапы, мониторинг, контролируемая миграция |

**Важно:** Preview/Staging с отдельными Neon-ветками описаны как **целевое требование**, а не как уже проверенная текущая интеграция.

## 5. Распределение ответственности

- **GitHub:** единственный источник исходного кода и истории разработки, PR, ревью и политики веток.
- **GitHub Actions:** проверка качества и безопасности; контролируемые workflow, в том числе для миграций при отдельном разрешении.
- **Vercel:** сборка, публикация, HTTPS, Next.js и серверные маршруты; управление переменными окружения.
- **Neon:** основная PostgreSQL, транзакции, миграции, резервирование и ветки базы данных.
- **Домен/DNS:** внешний публичный адрес, направление трафика к Vercel, проверка HTTPS.
- **Приложение:** авторизация, права доступа, валидация, предотвращение утечек данных, безопасность API и бизнес-логика.

## 7. Архитектурные цепочки

**Разработка и публикация:**

```text
Локальная разработка → GitHub (ветка / PR) → GitHub Actions → Vercel ↔ Neon
                                    └→ Preview + изолированная Neon Staging
```

**Работа пользователя:**

```text
Пользователь → Домен / DNS → Vercel → Next.js / серверная логика → Neon PostgreSQL
```

Таким образом, целевая архитектура промышленной эксплуатации — это автоматизированная публикация при строгих CI-проверках, разделённые среды, контролируемые миграции, секреты, наблюдаемость и независимый механизм восстановления. Каждый компонент переводится из категории «планируется» в «реализован» только после документированной проверки.
