# Этап № 4 — единое ядро военных черновиков: реализация первой итерации

Дата: 29.10.2026. Проект: ПравоПоиск. PR #25, ветка `feature/military-rebuild-from-zero-20261027`.

## Реализовано в коде

1. **121/121 планов документа:** `src/data/military-document-core.ts` строит спецификацию `MilitaryDraftPlan` для каждой из 121 документных и смешанных ситуаций из матрицы. Информационные 22 ситуации возвращают `null` и не получают генератора. Планы содержат однозначные URL связанных ситуаций (не выдуманные URL документов), тип, индивидуальное название, поля, адресат, доказательства и условную альтернативу.
2. **Общий семейный формат:** черновики 18 ранее реализованных прототипов формируются через `createMilitaryDraftPrototype()` в `DOCUMENT_RESULT_V1`, с `categorySlug="voennoe-pravo"`, `source="DETERMINISTIC"`, `legalRegistryReviewedAt=null`, `usedRuleIds=[]`, `filingReady=false`, `requiresLegalReview=true`.
3. **Валидация:** обязательны реквизиты заявителя, адресат и факты с минимальной длиной. Поддерживаются только объявленные поля; дополнительные необязательные поля для номера решения, имеющихся доказательств и приложений. Сведения ограничены по длине. Выбранная ситуация и требование из существующего прототипа не запрашиваются повторно.
4. **Условные ветки:** 38 альтернативных видов документа остаются метаданными, не выбираются автоматически; создание административного иска не происходит при одной лишь отметке альтернативы.
5. **Запрет автоматических «генераторов» для 103 случаев:** запрос на формирование отсутствующей индивидуальной композиции возвращает ошибку. `documentRequest` у этих планов пустой — юридическое требование не придумывается по заголовку статьи.
6. **Версии и данные:** повторно используется `addDocumentVersion`; максимум 6 снимков в оперативной памяти вкладки, без хранения фактов в URL, localStorage или отправки в отдельный сервис. Постоянного хранилища документы не получили.
7. **PDF/DOCX:** `src/lib/military-document-export.ts` использует имеющиеся `createMilitaryPdfBlob()` и `buildGeneratedDocumentDocxBlob()`. Экспорт проверяет тип, источник, привязку к прототипу, отсутствие официально подтверждённых норм и строгий маркер черновика. Файл содержит номер версии и «Юридическая сверка реестра: не проведена».
8. **Тесты:** `military-document-core.test.ts` проверяет 121 план, 18 прототипов, 103 отказа, 38 альтернатив, обязательные поля, 6 версий. `military-document-export.test.ts` проверяет невозможность подмены флагов, неправильный адрес документа, настоящие PDF/DOCX байты. Оба добавлены в `npm run test:military`.

## Ограничения

Этот результат представляет **рабочее ядро и внутренние прототипы**, а не запуск всех 121 юридических генераторов. Ни одна заявленная правовая норма автоматически не считается подтверждённой. Поля суда и ответчика в планах создаются только для судебного исхода и требуют самостоятельной проверки процессуального порядка. В 18 прототипах сохраняется прежний авторский текст, который ещё должен пройти юридическую приёмку.

PDF/DOCX создаются через имеющиеся библиотеки, но экспорт не включён в боевые страницы. Отдельные тесты должны пройти GitHub Actions после последнего коммита. Смена ветки Coolify, релиз в `infra/coolify-russian-vps`, изменения VPS, секретов, базы данных и продакшен-сайта не выполнялись.

## Следующие действия

- Для 103 отсутствующих композиций составить конкретные юридические требования, правила адресации, приложения и проверяемые поля; не применять универсальную жалобу к процессуальным судебным документам.
- Проверить источники, редакции и процессуальные правила, затем пройти юридический gate каждой ситуации.
- Подключить проверенные планы к компонентам пользовательского маршрута, не публикуя неутверждённые формы как готовые к подаче.
- Проверить печатные PDF/DOCX, версионность, редактирование и переходы при реальном QA в отдельном тестовом окружении Coolify.
