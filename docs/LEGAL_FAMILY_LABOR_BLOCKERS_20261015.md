# Отдельный отчёт: ограничения полной приёмки семейного и трудового права

**Дата проверки:** 15.10.2026  
**Ветка исправлений:** `fix/family-labor-audit-hardening-20261015`  
**Охват:** 29 семейных маршрутов (24 исходных + 5 дополнительных), 14 трудовых маршрутов, 50 трудовых сценариев, 21 дополнительный семейный сценарий.

## 1. Технические исправления этого этапа

1. Трудовые анкеты: общий типизированный реестр полей UI/API; на сервере проверяются все обязательные ключи и их подписи, отсутствие дубликатов/чужих полей/пустых значений, настоящая календарная дата; значения передаются генератору в каноническом порядке.
2. Добавлены негативные тесты каждой из 50 трудовых анкет, в том числе подмены полей, некорректных дат и дублирования.
3. Трудовые правовые ссылки: проверка всех номеров статьи в перечислениях и коротких диапазонах; разрешённые статьи берутся **только** из правил, указанных генератором в `usedRuleIds`.
4. Дополнительные семейные маршруты: `usedRuleIds` сохраняются для норм, которые **действительно входят в текст документа**, без выдумывания оснований для официальных форм и подготовленных сведений.
5. CI: убрана команда `npx prisma db push`, которая выполнялась после `prisma migrate deploy` и могла скрывать отсутствие нужных миграций в контролируемой схеме. В проверках добавлены трудовые тесты.

**Статус:** правки кода в ветке; результаты PR CI и E2E фиксируются отдельно. Это не автоматическое доказательство правильности материального права.

## 3. Стандарт приёмки конкретного сценария (не переносить статусы между сценариями)

Для каждой комбинации `categorySlug / problemSlug / scenarioKey` получить отдельную запись:

- URL и переходы: **PASS/FAIL** — категория → ситуация → сценарий → документ → результат.
- Анкета: **PASS/FAIL** — зависимые и обязательные поля, проверка форматов, работа на сервере.
- Правовой исход: **LEGAL_REVIEW_PASS/FAIL/PENDING** — действующие официальные нормы и их применимость, сроки, подсудность, льготы и исключения.
- Документы: **PASS/FAIL** — PDF/DOCX соответствует проверенному сценарию, не содержит вымышленных фактов, готовность к подаче не присваивается автоматически.
- Защита: **PASS/FAIL** — отсутствие личных данных в URL/логах, корректные права, архив/удаление.
- Проверка на настоящем провайдере (если AI): **PASS/FAIL/BLOCKED**.
- Повторный E2E после сборки и миграций: **PASS/FAIL**.

**Итог `LEGAL_REVIEW_PASS` не вытекает из `AUTOMATED_PASS`. До закрытия блокирующих требований `filingReady=false` остаётся обязательным.**

## 5. Решение по качеству

Изменения можно принять после зелёного CI как **усиление технической безопасности и проверяемости**. Нельзя при этом закрывать полную юридическую приёмку двух направлений до выполнения критериев раздела 2. Не изменять рабочую Neon PostgreSQL, не запускать `prisma db seed`, не включать `filingReady=true` без экспертного решения.
