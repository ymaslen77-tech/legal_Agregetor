# Военное право — сохранение версий в кабинете и полный браузерный QA (29.10.2026)

**Ветка:** `feature/military-rebuild-from-zero-20261027`. **PR:** #25 (Draft).

## Реализовано

### 1. Защищённое сохранение черновиков

- Переиспользован существующий архив `SavedLegalDocument` в PostgreSQL, штатные `/api/account/documents/` POST/GET/DELETE и идентификаторы версий `DOCUMENT_RESULT_V1`. Новой базы, миграций и отдельной таблицы нет.
- Пользователь явно нажимает «Сохранить в мои документы». До этого данные остаются в памяти вкладки. При несохранённой редакции отправка блокируется; после редактирования создаётся новый `versionId`.
- API разрешает новые военные черновики **только** в `NODE_ENV=development` при `ENABLE_MILITARY_DRAFT_PREVIEW=true`. В production загрузка новых черновиков через этот путь отклоняется, даже если переменную флага ошибочно включили.
- Валидатор проверяет точное соответствие категории, маршрута, ситуации, заголовка, `documentSlug` и версии генератора внутреннему плану; не принимает `AI_DRAFT`, фиктивно подтверждённые законы, подменённый заголовок или текст, потерявший предупреждение «ЧЕРНОВИК — НЕ ГОТОВ К ПОДАЧЕ».
- Используются существующие аутентификация, проверка `role === USER`, CSRF/origin-защита, ограничение размера запроса и rate limit. Хранилище применяет AES-256-GCM, отдельный случайный nonce, ассоциированные данные `ownerId+versionId`, ключ `DOCUMENT_STORAGE_KEY`. Подлинные значения ключей и персональные сведения не добавлены в GitHub.
- Кабинет дополнен категорией «Военное право», ссылкой на страницу ситуации и PDF/DOCX из сохранённой черновой версии. Статус «не готов к подаче» сохраняется после выгрузки.
- Для сохранённой версии в кабинете добавлен редактор, только при серверном `isMilitaryDraftPreviewEnabled(process.env)`: пользователь может подготовить исправленный текст, получить **новый независимый `versionId`** и явно сохранить его. Оригинальный архивный документ при этом не перезаписывается. Несохранённая редакция не передаётся автоматически в API.

### 2. Проверка всех 121 форм в браузере

- `tests/e2e/military-draft-all.spec.ts` создаёт отдельный тест для каждой из 121 ситуаций с документом: открытие страницы, видимость тестового редактора, проверка перечня требуемых полей, заполнение синтетическими данными, генерация текста, проверка его индивидуальной просьбы, маркировки «не готов к подаче», доступности PDF/DOCX.
- Запуск разделён на четыре CI-шарда `browser-all (1..4)` через `.github/workflows/military-preview-qa.yml` на локальном dev-сервере, без базы аккаунтов и без реальных документов.
- `tests/e2e/military-draft-preview.spec.ts` дополнен сценарием: до нажатия «Сохранить» запросов POST нет; затем в POST передаётся только явно выбранная версия с `filingReady=false`, `usedRuleIds=[]`; исправленная версия сохраняется с новым ID. Сетевой запрос к архиву перехватывается тестом и не затрагивает настоящую БД.
- `src/lib/military-saved-document.test.ts` проверяет валидность 121 версии для локального QA, отказ при флаге вне dev, отсутствие фиктивной юридической приёмки, проверку шифрования, отказ при чужом владельце и при подмене `versionId`.
- `tests/e2e/military-account-persistence.spec.ts` дополнен проверкой редактирования архива: исходная версия остаётся неизменной, новая версия записывается отдельным зашифрованным объектом, обе доступны только владельцу и обе могут быть удалены. Проверка проходит через настоящие HTTP API в одноразовом CI Postgres. Данный расширенный сценарий введён после первого успешного прогона и требует повторного выполнения.
- `tests/e2e/military-account-persistence.spec.ts` отдельно проверяет **настоящую** авторизованную запись через `/api/account/documents/`, выдачу версии, разграничение прав двух синтетических пользователей, удаление и очистку в изолированной PostgreSQL 17 (GitHub Actions). Все миграции применяются к одноразовому контейнеру. Ключи `JWT_SECRET` и `DOCUMENT_STORAGE_KEY` создаются случайно только для этого прогона; реальные секреты и VPS не используются. Результат: [успешная интеграционная проверка](https://github.com/ymaslen77-tech/legal_Agregetor/actions/runs/40905608984).
- Тест добавлен в `npm run test:military`. Экспорт PDF/DOCX ранее проверен бинарными тестами; сохранённые файлы не могут быть представлены как юридически утверждённые.

## Что эта реализация НЕ означает

- Настоящая запись **синтетических** данных на **временной PostgreSQL в GitHub CI** протестирована. На российском VPS и в рабочую PostgreSQL записи не производились: перед изолированным VPS-QA требуется отдельно подтвердить размещение и доступы к БД, `DATABASE_URL`, `DOCUMENT_STORAGE_KEY` и защиту персональных данных.
- Нет юридической приёмки 143 ситуаций и 121 текстов, а также проверки официальной редакции каждой нормы. Все три отдельных счётчика публичного выпуска остаются нулевыми.
- Поскольку новые военные генераторы доступны только в локальном development, они **не выложены** на `pravopoisk.ru`; нельзя считать их функциональностью действующего сервиса.
- Не выполнялись миграции БД, деплой, изменения секретов, переключение ветки `infra/coolify-russian-vps`, merge PR или выпуск.
- Запланированный предпродакшен-аудит должен покрывать авторизацию и права доступа к версиям между разными пользователями, ограничение архива в 100 версий, защиту от превышения лимитов, резервное копирование/восстановление и хранение ПД в России.

## Критерии для следующего релизного решения

1. Все CI по последнему commit SHA без ошибок: typecheck, lint, `test:military`, Next.js build, legal/document/reference route CI, браузерные 121/121 + сохранение новой версии.
2. Экспертная юридическая проверка нормативного реестра, квалификации каждого документа и процессуального порядка; ни один статус не повышать автоматически.
3. Изолированный, защищённый от публичного доступа preview на российском VPS с тестовыми данными; проверить `DATABASE_URL`, `DOCUMENT_STORAGE_KEY` и требования к персональным данным.
4. Только после этого — публичные страницы и финальный деплой под отдельным согласованным планом отката.

**Без выполнения критериев 2–3 PR сохраняет Draft и `productionReady=false`.**
